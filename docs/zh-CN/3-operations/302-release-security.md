# 302 — 发布安全

[English](../../3-operations/302-release-security.md)

Telegram Bot Token、API Hash、手机号、会话文件、本地配置、数据库、日志、下载内容、消息摘要和私有部署标识都属于非公开数据。

## 首次公开发布前

1. 使用专用密钥扫描器检查工作树、暂存区、忽略文件、所有本地/远端 Git 引用及可达 blob。
2. 在不输出值的前提下，将已知本地凭据值与 Git 对象比较；即使文件后来删除，匹配也必须轮换凭据。
3. 确认远端 URL 没有内嵌凭据。
4. 从准确候选提交构建 `git archive`、sdist 和 wheel，并按下方制品契约解压、扫描每个载荷。
5. 构建容器并检查文件清单和镜像层中是否包含配置、会话、数据库、下载内容或已知凭据值。
6. 检查生成的 Compose 配置，但不得公开展开后的环境变量值。
7. 运行 Ruff、格式、测试、依赖审计、文档链接验证和 Gitleaks；解决命中或记录范围严格的误报允许项。
8. 接受外部贡献前启用仓库密钥扫描、push protection、依赖告警和分支保护。

## 发布制品

包选择属于双层安全边界。`pyproject.toml` 中的 Hatch 选择器把运行时包输入限定为 `src/tgharbor/**/*.py` 下的 Python 源码路径，但选择器并不知道某个 Python 模块是否经过评审。独立的准确制品成员安全门强制制品与显式评审的运行时清单相等，并拒绝未知 Python 模块；两层缺一不可。任意文本、JSON、YAML、归档及其他包数据都不是运行时载荷。sdist 还只允许 `pyproject.toml`、`README.md`、`LICENSE`、`CHANGELOG.md`、公开构建辅助文件 `hatch_build.py` 以及构建器生成的 `PKG-INFO`。该辅助文件移除 Hatchling 强制加入的 VCS ignore 元数据，并被打包以便解压后的 sdist 能重新构建两类制品。wheel 把 `src/tgharbor/**` 映射为 `tgharbor/**`，并且只允许显式评审的 Python 清单、`.dist-info` 元数据和许可证。

发布构建不得禁用必需的 Hatch 构建钩子。被修改的环境能够禁用或更改钩子，因此仅靠后端配置不是强制执行点；准确制品成员安全门必须拒绝 `.gitignore`、未知 Python 模块、重复成员或其他任何额外路径。每次有意新增运行时模块，都必须评审并显式更新清单测试。

针对准确候选提交：

1. 把 `git archive`、sdist 和 wheel 构建到临时目录。不得从脏工作区或其他提交构建。
2. 解压每个制品并断言完整成员清单，而不只是检查已知坏名称不存在。必须拒绝 `.env`、真实或示例配置与 Compose 文件、已发布项目树之外的材料或未跟踪材料、测试、完整文档、会话、数据库、日志、下载数据、重复成员、绝对或路径穿越成员，以及符号链接或硬链接成员。
3. 验证发行名称、版本、`Requires-Python`，并确认 wheel 可在全新临时环境中安装并导入预期版本。
4. 在发布记录中记录制品文件名、大小、SHA-256 和版本。需要新制品时，必须从同一不可变候选重新构建并比较哈希。
5. 保持 `tests/test_distribution_artifacts.py` 通过；它会直接构建制品，从解压后的 sdist 重新构建两类制品，安装两条 wheel 路径，并覆盖中性文件、未知 Python 文件、本地根载荷、禁用钩子、重复成员、路径和链接等对抗场景。

在命令尚未针对准确候选实际运行前，不得声称制品或安全门已通过。Git ignore 和 Docker ignore 文件不是包安全边界。

## 容器身份与来源

可移植 Compose 示例使用准确发布标签 `tgharbor:0.2.3`。容器标签是别名，不能取代已记录的镜像摘要。发布工作流把准确版本标签和提交标签视为不可变身份，只把次版本标签和 `latest` 视为仅向前移动的可变别名。Dockerfile 提供安全的本地默认值：版本 `0.2.3`、revision `uncommitted`、source `local`，created 时间戳为 Unix epoch。这些 revision、source 与 created 默认值表示非发布构建，发布镜像禁止使用。

### 注册表标签策略

准确发布版本（`0.2.3`）和准确提交身份（`sha-<提交 SHA 前 12 个字符>`）不可变。若任一目标标签已存在，工作流会在注册表登录、构建或推送之前失败关闭。不得覆盖或复用不可变版本标签或 `sha-*` 标签。

派生的次版本标签（`0.2`）和 `latest` 是可变的别名。它们可以不存在。如果存在，别名只能从同一仓库中已验证的较旧发布向前移动。在注册表登录前，工作流解析完整分页的 Docker Hub 标签目录以及每个别名的摘要。对于每个存在的别名，必须满足：

- 别名摘要至少由一个低于候选版本的已发布稳定 `MAJOR.MINOR.PATCH` 标签和至少一个不可变 `sha-*` 标签共同使用；
- 次版本别名指向同一主版本和次版本系列中最高已发布稳定版本，并且候选补丁版本更高；
- `latest` 指向整体最高已发布稳定版本，并且候选版本更高；以及
- 当存在多个别名时，它们必须同意同一个摘要。

即使两个可变别名都不存在，候选版本也必须高于仓库中整体最高已发布稳定语义版本。该全局单调规则阻止在别名删除后回填较旧的不可变版本。

稳定标签与 `sha-*` 标签共享同一摘要只是命名约定。因此，登录前工作流会匿名通过注册表 API 解析每个存在的别名并验证其实际 OCI 身份。两个支持的平台镜像（`linux/amd64` 和 `linux/arm64`）必须一致报告规范项目源码、与共享索引摘要的最高稳定标签相等的版本，以及一个完整 40 字符 revision，其前 12 个字符与共享该摘要的 `sha-*` 标签完全一致。缺失或重复平台、平台标签分歧、缺失或格式错误的标签或媒体类型、平台清单或配置摘要/正文不匹配、超大响应、不支持的索引结构，以及注册表、认证或网络错误都会失败关闭。仅伪造稳定标签加 `sha-*` 命名而没有匹配的镜像身份不会被接受。

如果多个稳定标签共享别名摘要，则使用其中最高匹配版本，但别名仍必须等于其范围内最高已发布稳定版本。工作流会拒绝以下别名：指向没有稳定版本身份的摘要、指向没有 `sha-*` 身份的摘要、指向相同或更新版本、指向非最高或回滚版本、次版本别名指向错误的主/次版本、别名彼此不一致、未知或格式错误的标签、重复元数据、分页截断或计数不一致。任何 Docker Hub API 或注册表错误都是致命的；登录前检查不发送凭据。别名策略绝不会写入稳定版本标签或 `sha-*` 标签。

登录前的目录读取不是原子比较并交换。工作流无法阻止验证后发生的并发注册表变更。工作流会在注册表登录前立即重新检查别名，推送后验证只有在四个目标标签（`0.2.3`、`0.2`、`latest` 和 `sha-<前 12 个字符>`）全部解析到同一个新 OCI index 摘要，并具备所需 OCI 标签、来源证明、SBOM 和运行时冒烟结果时才通过。推送后检查失败会阻止发布，需要调查或发布新的补丁版本；它绝不授权把不可变标签或可变别名向后移动。

发布镜像必须从干净的不可变候选构建。工作流构建上下文使用已校验的完整提交 SHA，而不是可变发布标签引用；构建前仍会验证标签可达性和准确 CI 运行。把 `TGHARBOR_IMAGE_SOURCE` 设为已验证的规范公共源码 URL，不得硬编码非公开源码 URL；把 `TGHARBOR_IMAGE_CREATED` 一次性设为 RFC 3339 UTC 格式的候选构建时间。必须提供完整候选提交：

```bash
CANDIDATE_COMMIT="$(git rev-parse HEAD)"
test -z "$(git status --porcelain)"
test -n "$TGHARBOR_IMAGE_SOURCE"
test -n "$TGHARBOR_IMAGE_CREATED"
docker build --pull \
  --build-arg TGHARBOR_IMAGE_VERSION=0.2.3 \
  --build-arg TGHARBOR_IMAGE_REVISION="$CANDIDATE_COMMIT" \
  --build-arg TGHARBOR_IMAGE_SOURCE="$TGHARBOR_IMAGE_SOURCE" \
  --build-arg TGHARBOR_IMAGE_CREATED="$TGHARBOR_IMAGE_CREATED" \
  --tag tgharbor:0.2.3 .
```

检查生成的 OCI 标签，并要求 title 为 `TGHarbor`、version 为 `0.2.3`、revision 为准确候选提交、source 为已验证公共来源、license 为 `Apache-2.0`，created 为所提供时间戳。推送后来源证明必须结构化绑定 BuildKit 源码 URI 及其 `sha1` 提交到规范源码和发布 revision；仅出现在构建参数、内部参数或其他无关字段中的源码或 revision 字符串不满足检查。把镜像摘要与标签值一同记录，再运行最终文件系统、配置/历史和逐层扫描。必须从不可变候选重新构建发布镜像，不得依赖可变标签。Docker 不可用时，实际容器构建仍是未通过状态；静态 Dockerfile 测试不能替代候选安全门。完成此源码/容器发布安全门不代表批准生产上线；生产上线仍需独立的恢复与部署验收。

凭据或会话可能泄露时必须先撤销或轮换。重写历史不能让仍有效的凭据变安全。与所有仓库用户协调历史重写，并在完成后重新扫描所有引用。

## 持续控制

CI 使用只读仓库权限，检出完整历史，将 Action 固定到不可变提交 SHA，并运行依赖审计与密钥扫描。无凭据的验证任务可以从受保护默认分支开始，但它会解析并输出该分支的准确提交 SHA；带凭据的发布任务使用该准确 SHA 检出工作流源码，而不是可变的 `master`。它还会运行 `.github/scripts/verify_publication_boundary.py`，在出现以下情况时使构建失败：已跟踪或可达历史中存在不安全路径、公共链接指向受限或未跟踪材料、公共文档或工作流中存在符号链接、制品上传缺少精确成员白名单，或构建上下文不是“默认拒绝 + 白名单”结构。Dependabot 每周为 Python、Action 和 Docker 依赖创建数量受限的更新。

密钥扫描把固定版本 Gitleaks CLI `8.30.1` 安装到 `$RUNNER_TEMP`，不再运行市场 Action；解压前校验官方 `linux_x64` 归档的 SHA-256 `551f6fc83ea457d62a0d98237cbad105af8d557003051f41f3e7ca7b3f2470eb`，且不向扫描器传递任何 Token 或 License 密钥。扫描对象是检出仓库的完整可达历史，而不是 push、Pull Request 或 tag 事件范围，因此初始分支推送、普通推送、Pull Request 与 tag 推送都经过同一完整历史安全门。未检出提交或检出为浅克隆时，扫描拒绝报告干净结果。命中输出执行 100% 脱敏，不使用横幅或颜色，并使用退出码 `2`；命中以密钥事件使任务失败，其他任何非零退出都报告为扫描器运行故障，绝不能被描述为扫描干净。

不得把密钥、会话文件、消息内容、私有链接、数据库行或原始诊断对象粘贴到 Issue 或 PR。维护者公开联系方式后，安全报告应使用 `SECURITY.md` 中的私密流程。

## 发布记录

在发布记录中记录扫描器版本及其固定归档校验和、引用数、对象数、镜像摘要、候选提交、制品名称、大小、SHA-256、版本、命令、结果、误报判断和轮换情况。不得记录凭据值、私有主机名、账号 ID 或用户内容路径。
