# 303 — v0.2 升级与回滚

[English](../../3-operations/303-v0-2-upgrade.md)

本指南会把 SQLite schema 1、2 或 3 升级到 4，并把 v0.1 UUID 目录中已跟踪的完成文件移入共享 Inbox。Schema v4 增加了可空的交互提示消息锚点，用于编辑优先的提示与原地分页。持久结果投递只复用这些交互行与步骤值；schema 仍为版本 4，该行为无需迁移。生产升级前必须先对副本演练。

已经使用 schema 4 的部署无需迁移步骤。按下方说明备份并停止服务，然后启动 0.2.3 构建；初始化会确认 schema 版本为 4，且不更改任何表。支持 schema 4 的构建仍会拒绝 `user_version` 高于 4 的数据库，而不会猜测未知结构。

## 从已发布的 v0.2.2 升级

`0.2.2` 部署使用 SQLite schema 2。首次启动 `0.2.3` 时会通过 v2 → v3 → v4 链条自动升级到 schema 4。无需手工 SQL、迁移命令或新增配置键。

1. 先完成“升级前”所述的备份。该恢复点必须在首次启动 `0.2.3` 之前存在并已验证，因为升级无法原地回退。
2. 使用现有数据目录启动 `0.2.3`。初始化会为每个 schema 版本使用一个显式事务，并在首个失败步骤回滚该步骤后停止，保留最后完成的版本。
3. 兼容性是单向的。`0.2.2` 构建无法打开 schema 4 数据库，因此回滚意味着同时从备份恢复升级前的数据库、旁文件、会话、配置和完整下载根目录，然后再次启动 `0.2.2`。不要让不同版本共用同一数据目录，也不要把 schema 4 数据库复制到升级前的下载根目录。
4. 在把服务交还用户前，用下列检查验证升级。

该路径的升级验证：

- 数据库报告 schema 版本 4，且启动日志没有迁移错误。
- `/status` 会列出请求者的任务；因升级中断的任务在请求者继续前显示为暂停。
- 每个授权用户收到一条启动消息，包含包版本、带时区的服务器本地时间戳及其自身暂停数量。继续只恢复该用户的任务，重复继续会报告零且不报错。
- 测试下载进入 Inbox，保留、重命名、归档、目录与批次操作会编辑来源卡片，并可跨重启保留。
- 已完成的多成员相册对每个请求者只产生一条批次通知，部分移动后保留持久 Retry 操作。
- Legacy 对账没有无法解释的失败，文件数与字节总数与备份清单一致。
- 交互状态、待处理结果和重试卡片在重启后恢复，且不重跑整理。

“生产验证”下更长的清单覆盖本发布剩余的交互、分页与投递检查。

## 升级前

1. 停止 TGHarbor，确认没有进程持有实例锁。
2. 备份 SQLite 数据库及旁文件、Telegram 会话、配置和完整下载根目录，并保留所有权与权限。
3. 把数据库和下载根目录备份视为同一个恢复点。
4. 在隔离环境中安装包含 schema v4 的候选构建并扫描发布制品/镜像。容器升级必须验证镜像标签解析到已记录的候选摘要，且 OCI revision 标签等于准确候选提交；标签本身不构成来源证明。

## 演练

让新应用使用复制的状态运行。初始化会为每个 schema 版本使用一个显式 SQLite 事务；失败步骤会回滚该步骤并停止初始化。随后恢复待完成的整理意图，并逐个对账 legacy 完成文件。不会覆盖无关 Inbox 文件；有歧义的目录、符号链接、已变化文件和冲突项保持原样等待检查。

只记录 schema 版本、发现/成功/失败数量、文件数量和权限结果。不要把文件名、消息摘要、私有链接或原始数据库行粘贴到公开日志或 Issue。

## 生产验证

- Schema 版本为 4，服务启动时无迁移错误。
- 从 schema v3 迁移的交互具有 NULL 提示锚点，新提示会获得锚点，且消息 ID 不进入回调或日志。
- `/files` 与 `/history` 的下一页和上一页会编辑来源列表消息；成功编辑不产生重复，重放的分页按钮属于陈旧请求，无法编辑的消息会产生恰好一条带有效按钮的替换列表，而超时或模糊编辑失败会保留旧分页可用且不重复发送。分页回调会在创建后继交互前原子消耗其准确、已授权、未过期且动作与步骤匹配的交互，因此并发回调只会产生一次编辑、一组后继交互，其他回调为陈旧。后继以回调消息为初始锚点，同一消息编辑无需重新绑定；投递受 shielding 保护并在重新抛出取消前提交。回退替换会在受 shielding 保护的关键区内移动所有后继锚点；若重新绑定失败，会禁用替换、删除后继、恢复准确的原始交互，并重新渲染其来源标记（或发送一条重试卡片并绑定）。投递前失败或取消会删除后继并恢复准确的原始交互，除非原交互在投递期间已过期。每个可见分页标记都应解析到持久活动行。
- 文本回复会尽可能编辑已存储的提示消息。只有可证明无法编辑的消息才回退为恰好一条替换消息；提示锚点重新绑定是针对预期当前锚点的比较并交换，失败的替换消息会被禁用且不替换活动卡片。所有保留 Back、Cancel、Retry、目录或分页控制的卡片都使用同一辅助函数，因此点击替换卡片上的控制可用。
- 完成卡片操作通过目录选择、新建目录提示、确认、可见工作状态和结果编辑来源消息。Back 返回目录选择，Cancel 在目录选择/提示/确认中可用，无效或斜杠前缀目录输入会停留在提示并显示相对路径示例，保留操作会保留完成摘要。重复确认回调会报告正在处理，且只执行一次文件库操作；可恢复失败会恢复确认或重试状态并渲染 Back/Cancel 或 Retry/Cancel 控制。领取工作状态后，文件库变更及其到 pending 的立即转换构成一个取消安全关键区，包括新建目录与批次整理；工作开始后的外部取消先稳定操作与 pending 写入再传播，提交前失败可恢复之前的确认与锚点，已提交效果绝不恢复重复动作。这只是异步取消保证；文件系统与目录边界之间发生 SIGKILL 或掉电时依赖幂等对账与重放。已提交的单文件结果或终态批次结果为不可操作的 `result-pending`；部分批次结果为不可操作的 `retry-pending`，只有在 Retry 卡片已知送达且实际锚点完成比较并交换后才变为 `ready`，并写入新的可操作生命周期。终态行只有在已知送达并通过预期步骤与预期锚点比较并删除后才移除；发送成功但没有正消息标识属于模糊投递并保留该行。全部待处理结果只在存储整理对账后列出，并在回调处理前按当前已授权目录状态恢复而不重跑整理；没有固定积压上限，未授权行跳过并保留，模糊失败保留到下次启动。重启会原子恢复持久化的 `working-confirm`/`working-confirm-new-directory` 行到准确的原确认，并把旧式通用 `working` 行恢复到 `ready`；即使原过期时间已过也会恢复，并写入新的可操作生命周期，且在处理回调前返回恢复会话。Telegram 启动后，Bot 会把每个恢复锚点编辑为可见卡片：确认显示待定名称/目录上下文及 Confirm、Back、Cancel；新目录显示 Create and move；旧式就绪行显示带相应 Choose folder 或 Retry move 控制及 Cancel 的中断动作卡片。锚点缺失或可证明无法编辑时发送一条替换并通过比较并交换绑定。按会话隔离的失败只记录步骤、结果、类别和错误类型，不中止启动、不改变任务状态，并保持恢复行可通过 `/files`、`/history`、`/dirs`、`/rename` 或 `/archive` 继续。
- 成功的单文件或终态批次整理会保留不可操作的 `result-pending` 行，直到最终卡片已知送达。部分批次结果保留 `retry-pending`，直到 Retry 卡片已知送达且实际锚点完成比较并交换，随后变为可操作 `ready` 并写入新的可操作过期时间。提交后强制最终编辑或替换发送失败必须保留 pending 行且不产生重复替换；发送成功但没有正消息标识属于模糊投递并保留 pending；模糊失败会保留到下次启动。重启按当前目录状态恢复卡片且不重跑整理，重试只移动仍在 Inbox 的成员。全部 pending 行都会列出，没有固定积压上限，因此反复失败的行不会饿死后面的行。未授权 pending 行会被跳过并保留。重复的相同移动和重复创建已存在的目录不会追加重复审计行。schema 仍为版本 4，无需迁移。
- 每个操作者只有一个活动文本工作流。原子激活不会影响分页按钮和其他完成卡片，并发激活绝不会留下零个活动工作流；无任务标记的 `/cancel` 会取消当前提示。
- 命令菜单注册会报告默认作用域与全部私聊作用域。强制单个作用域失败时只记录结果、作用域和错误类型，启动与键入命令继续可用；日志中不出现用户 ID。
- Legacy 对账没有无法解释的失败。
- 文件数和字节总数与演练及备份清单一致。
- `/status`、`/history`、`/files`、`/dirs`、`/stats` 返回符合范围的数据。
- 测试下载进入 Inbox，保留/重命名/归档操作可跨重启继续。
- 重命名/归档审计包含实际授权 Telegram 操作者 ID。
- 符合条件的中断任务会计为暂停 pending 任务，并在提交者继续前不被领取；耗尽和已取消的中断任务处于终态。
- 每个配置的授权用户会收到一条尽力发送的启动消息，包含包版本、带时区的服务器本地 ISO 时间戳及其自身暂停数量。查看按请求者隔离；继续只恢复该用户暂停任务并唤醒 Worker。重复继续会报告零且不报错。
- 已完成的多成员相册最多产生一条 Move all 交互。现有目录按最近使用顺序及新建目录显示，确认后报告已移动、跳过和失败数量且不含宿主路径。目录按钮绑定所显示目录与顺序，因此列表变化会把旧选择作为陈旧请求拒绝；部分失败的结果会保留持久 `Retry move` 操作。
- 成功完成消息显示最终目录名称、逻辑 `/download/<相对父目录>`、存储大小、服务器本地开始/结束时间、耗时、平均速度、请求者及来源群组/频道或 `N/A`。

## Schema v4 备份与回滚

schema v4 备份是一个恢复点，包含 SQLite 数据库及旁文件、Telegram 会话、配置和完整下载根目录，包括 Inbox、Archive、partial/恢复状态、批次通知状态、带提示锚点的交互行和用户文件。恢复前验证校验和，并保留所有权与权限。

停止新进程，同时恢复升级前 SQLite 数据库、旁文件和完整下载根目录，再恢复旧应用版本。绝不能让旧应用打开 schema 4 数据库，也不能混用升级前数据库与对账后的下载根目录。不要把 schema 4 数据库复制到 v0.1/v0.2 下载根目录，反之亦然。失败演练或生产状态应留作私密诊断，不要删除有歧义的用户内容。

命令菜单属于尽力维护的客户端元数据，不是应用状态。旧应用不会注册整合后的菜单；Telegram 可能继续显示上次注册的菜单，直到该客户端清除或替换。后续版本会重新注册并收敛菜单。若菜单缺失或不完整，只检查结果/作用域/错误类型警告，并通过重新连接或重启重试；不要把用户 ID 写入日志。

若重启后恢复的确认或 Working 卡片缺失，检查只包含步骤、类别和错误类型的 `outcome=not-visible`。交互行已恢复且任务状态未变；使用 `/files` 或 `/history` 找到条目，再使用 `/rename`、`/archive`、`/dirs` 或 `/mkdir`。若分页卡片显示陈旧控制，使用可见的 Retry 控制或重新运行 `/files`/`/history`。不要手工编辑交互行，卡片出现前不要声称可见恢复成功。
