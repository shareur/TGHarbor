# 303 — v0.2 升级与回滚

[English](../../3-operations/303-v0-2-upgrade.md)

v0.2 会把 SQLite schema 1 升级到 2，并把 v0.1 UUID 目录中已跟踪的完成文件移入共享 Inbox。生产升级前必须先对副本演练。`0.2.2` 是仅涉及格式化的源码发布；当前容器镜像仍是已记录的 `0.2.1` 发布。

## 升级前

1. 停止 TGHarbor，确认没有进程持有实例锁。
2. 备份 SQLite 数据库及旁文件、Telegram 会话、配置和完整下载根目录，并保留所有权与权限。
3. 把数据库和下载根目录备份视为同一个恢复点。
4. 源码安装必须在隔离环境中安装 `0.2.2` 并扫描构建制品。`0.2.2` 是仅涉及格式化的源码发布，没有容器镜像，不改变运行时行为，除本节描述的 schema 1 到 2 升级外不需要额外迁移步骤。
5. 容器升级必须从 [Docker Hub](https://hub.docker.com/r/shareur/tgharbor) 拉取 `shareur/tgharbor:0.2.1`，验证其解析到已记录的候选摘要，且 OCI revision 标签等于准确候选提交；标签本身不构成来源证明。由于未发布 `0.2.2` 镜像，容器部署继续使用已记录的 `0.2.1` 镜像。

## 演练

让新应用使用复制的状态运行。初始化会在一个 SQLite 事务中完成 schema 迁移；随后恢复待完成的整理意图，并逐个对账 legacy 完成文件。不会覆盖无关 Inbox 文件；有歧义的目录、符号链接、已变化文件和冲突项保持原样等待检查。

只记录 schema 版本、发现/成功/失败数量、文件数量和权限结果。不要把文件名、消息摘要、私有链接或原始数据库行粘贴到公开日志或 Issue。

## 生产验证

- Schema 版本为 2，服务启动时无迁移错误。
- Legacy 对账没有无法解释的失败。
- 文件数和字节总数与演练及备份清单一致。
- `/status`、`/history`、`/files`、`/dirs`、`/stats` 返回符合范围的数据。
- 测试下载进入 Inbox，保留/重命名/归档操作可跨重启继续。
- 重命名/归档审计包含实际授权 Telegram 操作者 ID。

## 回滚

停止 v0.2 进程，同时恢复升级前 SQLite 数据库、旁文件和完整下载根目录，再恢复旧应用版本。绝不能让 v0.1 打开 schema 2 数据库，也不能混用升级前数据库与对账后的下载根目录。失败演练或生产状态应留作私密诊断，不要删除有歧义的用户内容。
