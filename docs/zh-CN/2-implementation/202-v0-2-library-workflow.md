# 202 — v0.2 文件库工作流

[English](../../2-implementation/202-v0-2-library-workflow.md)

## 范围

v0.2 在不改变 v0.1 Provider 边界的前提下提高开源发布安全性，并增加可读的共享文件库。

包含：受限展示元数据、仅活动任务状态和分页历史、共享 Inbox/Archive 目录、防冲突扁平完成下载、安全重命名/归档/建目录/列表/统计、带操作者审计的持久内联工作流、到 v4 的 schema 迁移与提示消息锚定、编辑优先回调反馈、能在最终编辑失败或取消及重启后存活的持久结果投递、原地分页、尝试计时与暂停重启继续、不透明批次身份、完成就绪判断与持久通知领取、相册接收与保守来源元数据、详细持久成功消息、授权批次整体 Inbox 整理与 Move all、启动初始化及查看/继续控制、旧输出对账及公开发布安全门禁。

不包含：频道历史抓取、任意外部 URL、跨文件系统归档根目录、超出授权用户集合的角色权限和完整 Telegram 消息正文。

## 交付顺序

1. 发布隐私、迁移、授权和回滚契约。
2. 审计当前树、历史、引用、镜像和发布制品；轮换已暴露密钥。
3. 增加发布安全自动化。
4. 增加到 v4 的事务式 schema 迁移与迁移测试。
5. 增加受限 Provider 元数据及筛选/分页查询。
6. 增加存储布局、目录、整理服务和旧输出对账。
7. 增加持久 Telegram 交互、可读展示和命令。
8. 增加相册接收、持久批次通知、详细完成消息和启动继续控制。
9. 重组公开文档并执行完整验证。
10. 备份部署状态、演练迁移、部署并验证回滚。

## 验收

- 已跟踪文件、Git 对象、远端引用、镜像层、生成配置和发布制品均不包含真实凭据、Telegram 会话、用户内容或私有部署标识。
- CI 使用最小权限，并对 push 与 pull request 运行 lint、测试、密钥扫描和依赖检查。
- schema 1、schema 2 与 schema 3 数据库事务式升级到 v4，不改变已有任务状态或交互意图。已有交互行获得 NULL 提示锚点。v3 到 v4 步骤失败会回滚，高于 v4 的 schema 继续被拒绝。
- 符合条件的中断运行任务变为普通领取会跳过的暂停 pending 任务；耗尽任务进入 failed，已持久化取消进入 cancelled。重复重启保持暂停，按提交者的全部或选定继续操作受授权、幂等并保留重试计数。
- 尝试在领取时记录新的开始时间，并在终态原子记录完成时间；完成通知使用完成事务中持久化的时间戳。成功消息使用最终目录名称、逻辑 `/download/<相对父目录>`、存储大小、转换为服务器本地 `HH:MM:SS` 的持久开始/结束时间；缺失值和原始来源对等方显示 `N/A`，绝不暴露宿主绝对路径。
- 相册接收为每条媒体只提交一次，共享不透明批次身份和准确相册大小；分组消息不会重复提交，单条消息仍为一个任务，批次身份和来源元数据不进入回调或日志。
- 群组/频道 ID 仅作为可选元数据，不在两者之间推导，私聊、不可用或有歧义时显示 `N/A`。只有成员数量精确匹配且全部成功的多成员批次才可领取一次通知；释放、陈旧领取恢复、`sent` 幂等，以及启动时和周期性重投的持久发件箱可防止永久丢失，且只有在经过调度器配置的陈旧间隔后才会原子地重新领取。交互只记录意图与回调身份，不构成送达证据：发送或标记失败会保留并复用同一交互，重试至少重投一次通知。由于 Telegram 发送与 SQLite 标记并非原子，两者之间崩溃或失败可能重复聊天通知，`sent` 是终态，适配器不声称跨系统的恰好一次送达。`Move all to new folder` 流程按最近使用顺序列出现有目录及新建目录，确认目标与创建，并报告已移动/跳过/失败数量且不含宿主路径。
- 授权批次整理只通过现有整理路径移动当前 Inbox 成员，报告不包含绝对路径的稳定逐文件类别，跳过已移动、缺失或未就绪成员，并可安全重放。部分或可重试结果持久化为 `retry-pending`，提供持久的 `Retry move` 操作，并且只有在卡片已知送达且实际锚点完成比较并交换后才变为可操作 `ready`；后续重试只移动仍在 Inbox 的成员。完全移动或全部已移动的结果（包括仅 missing 的结果）持久化为 `result-pending`，仅在终态卡片已知送达后移除。目录按钮携带绑定目录与显示顺序的不透明摘要，因此排序或成员变化会把旧选择作为陈旧请求拒绝且不产生变更。陈旧、过期、跨动作和跨请求者交互标记会被拒绝且不产生变更，回调在文件库操作前只确认一次，启动时绝不为了渲染结果而重跑批次整理。
- 交互提示会持久化内部 Bot 消息锚点，迁移行默认为 NULL，重新绑定是按请求者隔离且必须匹配预期当前锚点（包括 NULL）的比较并交换。文本输入会编辑存储的提示消息；所有保留 Back、Cancel、Retry、目录或分页控制的卡片都通过同一个编辑优先辅助函数投递，该函数取得实际编辑或替换后的消息 ID，并把锚点从预期旧 ID 比较并交换到该 ID。若消息可证明无法编辑，则发送恰好一条替换消息并绑定其消息 ID；比较并交换失败的替换消息会标记为陈旧。超时、flood wait、超长文本、模糊 RPC/网络错误和任意异常绝不重复发送。未修改的编辑视为成功；取消会被重新抛出。
- 完成卡片操作在目录选择、新建目录、相对路径提示、确认、工作状态和结果之间保持同一条消息锚点上的编辑优先。Back 返回目录选择；Cancel 在目录选择、提示和确认中可用。保留操作保留完成摘要并说明文件仍在 Inbox。无效或斜杠前缀目录输入会停留在提示并显示相对路径示例，且不创建任务。
- 每个操作者只有一个活动文本工作流。单个 `BEGIN IMMEDIATE` 激活会验证保留行、操作者、过期时间、动作和预期步骤，把它转换到目标等待/确认状态，然后才在同一事务中删除较早的活动文本工作流，同时不删除分页交互或就绪完成按钮。并发激活两行会恰好留下一个活动工作流，绝不会为零。文本路由先于链接提交；无标记的 `/cancel` 取消当前提示，而 `/cancel <id>` 保持任务取消。
- 确认工作通过把授权且未过期的交互从 `confirm` 原子转换为 `working-confirm`，或从 `confirm-new-directory` 转换为 `working-confirm-new-directory` 来领取；并发回调中恰好一个获胜。重复回调报告正在处理或陈旧，且不覆盖获胜者卡片。可恢复的单文件与批次失败会恢复确认或就绪重试状态，重新绑定任何替换后的 Back/Cancel/Retry 卡片并渲染其控制。成功会原子地把已领取行转换为不可操作的 `result-pending`，并删除该任务的其他完成动作行。结果文本按当前已授权的任务与目录状态重建，只有在已知投递成功并通过预期步骤与预期锚点比较并删除后才移除。终态卡片没有按钮；替换发送通过 pending 安全的 CAS 绑定实际锚点。文件库变更及其到 pending 的立即转换构成一个取消安全关键区，包括新建目录与批次整理；工作开始后的外部取消会让操作与 pending 写入完成后再传播，提交前失败可恢复准确的之前步骤与提示锚点，已提交效果绝不恢复重复动作。持久化、投递与成功清理一起受 shielding 保护，投递期间未知的客户端取消会向上传播而该行保持 pending，取消绝不会被吞掉；发送成功但没有正消息标识属于模糊投递，不会消耗终态行或用旧锚点提升重试行。这只是异步取消保证；文件系统与目录边界之间发生 SIGKILL 或掉电时依赖幂等对账与重放。一个原子启动恢复事务返回恢复后的会话。Telegram 启动后、回调处理器接受事件前，适配器尽力把每个锚点编辑为步骤绑定卡片：确认保留待定名称/目录上下文及 Confirm、Back、Cancel；`confirm-new-directory` 显示 Create and move；旧式 `working` 行成为带相应 Choose folder 或 Retry move 控制及 Cancel 的中断动作卡片。锚点缺失或可证明无法编辑时发送一条替换并通过比较并交换绑定。失败按会话隔离，只记录步骤、结果、类别和错误类型，不中止启动，也不改变任务状态。若编辑与发送均失败，恢复行仍可通过 `/files`、`/history`、`/dirs`、`/rename` 或 `/archive` 继续。
- pending 结果与重试行可跨重启存活，并且只在存储整理对账之后列出。适配器在回调处理器启动前恢复它们，重新检查当前授权，跳过并保留未授权行，隔离每个失败，绝不调用单文件或批次整理 API 来渲染结果。没有固定积压上限，因此即使较早的行反复失败，后面的行也会在同次启动中被尝试。已过期的 pending 行仍可恢复；被搁置的工作领取会以新的可操作生命周期恢复，其他已过期的可操作行保持陈旧；模糊或未知的投递失败会保留该行到下次启动。重复的相同移动和重复创建已存在的目录不会追加重复审计行。schema 仍为版本 4，此行为无需迁移。
- `/files` 与 `/history` 命令发送一条消息，而“下一页”和“上一页”回调会编辑来源 Bot 消息。分页回调先原子消耗其准确、已授权、未过期且动作与步骤仍匹配的交互，因此第一个并发回调拥有它，其他回调在创建后继或编辑之前即被视为陈旧。后继交互只在取得所有权后创建，并以回调消息为初始锚点。投递受 shielding 保护，并在重新抛出取消前提交，因此同一消息编辑无需重新绑定，可见后继卡片保持活动标记。可证明不可编辑的消息会产生一条带有效按钮的回退消息；所有后继锚点在受 shielding 保护的关键区内移动到替换消息。若重新绑定失败，会禁用替换、删除后继、恢复准确的原始交互，并重新渲染原卡片（或发送一条重试卡片并绑定），使恢复后的来源标记可见。投递前的非回退失败、超长渲染、模糊错误或取消会删除后继并恢复准确的原始交互（除非原交互在投递期间已过期）。未修改的编辑不产生重复；重放或并发消耗的分页标记保持陈旧且不产生变更；确认始终最先且只执行一次。投递日志只包含结果、投递方式、安全错误类别和延迟。
- 命令菜单使用准确的十一条命令注册默认作用域和全部私聊作用域，在 Bot 启动和控制器构造之后、启动通知与 Worker 稳态之前运行，并隔离每个作用域失败，日志只包含结果、作用域和错误类型。
- 已接受的链接/上传消息显示 `Download queued · <短 ID>`、来源、pending 状态和下一步 `/status` 指引；相册接收显示文件数、初始状态以及所有文件完成后才出现 Move all。详细完成与失败摘要把 `Job: <短 ID>` 紧接标题之后，且不改变其余字段顺序。
- 展示文本经过规范化且不超过 160 个 Unicode 字符；完整消息正文和敏感 Telegram 对象不会进入持久化或日志。
- 新下载完成到 `inbox/`，临时字节保留在 `.partial/`，同名文件绝不覆盖。
- 中断的完成或整理操作可在不删除用户内容的情况下对账；失败旧文件保留原路径供检查。
- `/status` 不显示终态任务；历史、文件、目录和统计有界或分页，并使用可读名称与大小。
- 每个授权用户都能整理共享文件库；重命名、归档和建目录记录操作者 ID。
- 完成动作在重启后继续有效，并明确拒绝未授权、过期、陈旧或冲突输入。
- 启动恢复把符合条件的中断任务标记为暂停后，向每个授权用户发送一条尽力发送的初始化消息，含版本、带时区的服务器本地 ISO 时间戳及其暂停数量。查看按请求者隔离；继续只恢复该用户暂停任务、唤醒 Worker 并可安全重放。单个聊天失败不中止启动，普通 pending 任务继续运行，重复重启保持未继续任务暂停。
- 测试拒绝路径遍历、绝对路径、符号链接、歧义短 ID、异常文件类型和覆盖尝试。
- 英文与中文文档、导航、示例和运维说明保持同步。

## 部署与回滚

停止服务并备份 SQLite 数据库、Telegram 会话和下载根目录。在副本上演练迁移与对账；只报告数量与失败，不记录内容或私有 Telegram 引用。

部署后验证 schema 版本 4、文件数、权限、暂停任务数量、每用户启动消息、查看/继续行为、活动任务、相册接收、详细完成消息、Move all 流程、共享命令、原地分页、带 Back/Cancel/工作状态的单卡片编辑优先流程、单活动文本工作流、命令菜单注册、提示编辑、回调恢复和容器稳定性。把 SQLite 数据库、旁文件、Telegram 会话和完整下载根目录作为一个 schema v4 一致性单元备份与恢复。回滚时停止新版本，同时恢复匹配的数据库与下载根目录备份后再启动旧应用。
