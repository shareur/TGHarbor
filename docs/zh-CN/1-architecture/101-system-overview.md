# 101 — 系统架构概览

[English](../../1-architecture/101-system-overview.md)

TGHarbor 将面向 Telegram 的接口与下载执行、共享文件库管理分离。

```text
Telegram Bot 与授权用户会话
                 |
                 v
        Job API / Library API
           |            |
           v            v
      持久队列      SQLite 目录与审计
           |
           v
  Worker -> Provider -> 本地存储
```

该图仅为概念示意。接口负责提交和查看工作；Provider 获取内容；存储保存文件；SQLite 保留队列与目录状态，使已接受的工作和完成文件能够跨正常重启保留。

## 组件职责

- **Telegram 适配器**接收 Bot 私聊消息，并通过独立的授权用户会话解析单条消息链接。
- **Job API** 创建并查询按请求者隔离的下载任务。
- **Library API** 提供共享的完成文件目录及整理操作。
- **队列与 Worker** 在接口处理之外执行下载。
- **Provider** 封装不同来源的获取行为。
- **存储**管理配置的本地下载根目录。

## Telegram 角色与授权

Bot 会话接收授权用户发送或转发的媒体，并下载 Bot 可见的消息。用户会话解析单条公开或私有 `https://t.me/` 消息链接；登录账号必须本来就有权访问该消息。

创建、查询或取消任务前都会检查 Telegram 用户 ID。任务始终按请求者隔离。Bot 只处理私聊；验证码和两步验证密码只能通过本地 `tgharbor login` 命令输入。

所有配置的授权用户共享完成文件的可见性和整理权限。变更操作会记录实际 Telegram 操作者 ID，并且不会从共享文件库权限推断任务所有权。共享文件库不是多租户隔离边界。

## 持久性与重启行为

已接受的任务是持久化的。正常重启不会丢失排队中的工作：符合条件的中断任务会作为新尝试继续，取消请求会被遵守，耗尽尝试次数的任务会失败。可重试失败使用有界延迟，更长的 Telegram 限流等待会被遵守。

中断的下载不保证从字节范围续传：部分字节可能被丢弃并重新下载。只有一个应用实例可以使用同一本地状态。Bot 终态通知为尽力发送，不能改变已持久化的结果。

## 存储安全

存储把配置的根目录划分为共享 `inbox/`、共享 `archive/` 和隐藏的 `.partial/`。完成下载首先进入 Inbox，授权用户再将其整理到 Archive。

路径必须保持在配置的根目录内。绝对路径、路径遍历、符号链接及异常文件系统对象类型都会被拒绝。目标冲突时会追加后缀，而不是覆盖已有文件。如果完成或整理操作中断，TGHarbor 会恢复安全结果，或将受影响文件保留给运维者检查，且不会删除用户内容。数据库目录和下载根目录必须作为一个一致性单元一起备份和恢复。
