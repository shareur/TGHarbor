# 101 — 系统架构概览

[English](../../1-architecture/101-system-overview.md)

TGHarbor 将外部接口与下载领域分离。

```text
Telegram / 未来的 REST API / CLI
              |
              v
           Job API
              |
              v
           持久队列
              |
              v
           Worker
              |
              v
          Provider
              |
              v
           Storage
```

## 原则

1. Telegram 是适配器，不是应用核心。
2. 下载任务是持久化的领域对象。
3. Worker 能在重启后恢复未完成的任务。
4. Provider 封装不同来源的下载行为。
5. 存储路由独立于 Provider。
6. UI/API 层不应持有下载状态。

共享文件库路径与下载状态所有权相互独立：

```text
Telegram Bot
     |
     v
 Library API ------> SQLite 目录与审计
     |                         |
     +-------------------------+
                   |
                   v
               本地存储
```

## Telegram 适配器

TGHarbor 在相同 Provider 契约后使用两个相互独立的 Telegram 会话：

- Bot 会话接收授权用户发送或转发的媒体或相册。相册由专用相册处理器只处理一次；单消息处理器忽略分组消息。随后下载 Bot 可见消息。
- 用户会话解析单条公开或私有 `https://t.me/` 消息链接。登录账号必须原本就有权访问该消息。

授权边界位于 Job API。创建、查询或取消任务前都会检查 Telegram 用户 ID，任务只能由提交者访问。Bot 只处理私聊；验证码和两步验证密码只能通过本地 `tgharbor login` 命令输入。

相册提交使用固定版本前缀、请求者 ID、配置的会话/客户端身份、来源聊天和 Telegram `grouped_id` 生成一个确定的不透明批次 ID。这些组件绝不进入回调载荷或日志。每条媒体成员使用同一 ID 和相册准确成员数。直接链接仅解析到相册一个成员时仍为单成员任务，不远程抓取相册。

Library API 构成第二个授权边界。所有配置的授权用户共享完成文件的可见性和整理权限。变更操作会记录实际 Telegram 操作者 ID、重新验证目录状态，并且不会从共享文件库权限推断任务所有权。

## 队列语义

```text
pending --领取--> running --成功--> completed
   |                 |  |
   |                 |  +--永久失败/次数耗尽--> failed
   |                 +-----可重试-------------> pending（延迟）
   +--取消------------------------------------> cancelled
running --观察到取消请求---------------------> cancelled
```

SQLite 保存状态、来源引用、提交者、有界显示元数据、尝试次数、进度、下次可用时间、Worker 所有权、错误和输出路径。一条 SQL 语句领取 pending 行并把它分配给一个 Worker。Worker 更新状态时同时检查任务 ID 与 Worker ID。TGHarbor 运行一个应用实例和多个异步 Worker；数据库旁的进程锁会拒绝第二个实例。

启动时，未耗尽尝试次数的中断任务回到 pending 并设置 `resume_required`。这些暂停任务不会被普通领取，必须由提交者列出并显式继续全部或选定任务。继续操作会清除暂停标记、保留尝试计数并唤醒 Worker；重复继续是幂等的。耗尽任务进入 failed，已持久化的取消请求进入 cancelled，普通 pending 任务不受影响。这是任务级重启恢复：部分文件会被丢弃，继续后重新下载，当前版本不保证字节级断点续传。

恢复完成且 Telegram 客户端可发送后，启动过程会向每个配置的授权用户发送一条尽力发送的私有初始化消息，包含包版本、带时区的服务器本地 ISO 时间戳及该请求者的暂停数量。数量大于零时附带持久的查看与继续交互；为零时说明没有中断任务并省略它们。单个聊天失败只记录通用错误，不中止启动，也不影响其他用户。Worker 先于这些通知启动，因此普通 pending 任务不会被阻塞，也不会执行第二次恢复。

每次尝试在领取时记录 `started_at`，并在完成、终态失败或取消时原子设置 `finished_at`。可重试失败会清除当前尝试开始时间，使后续耗时与速度只描述实际运行的尝试。完成事务中持久化的时间戳是权威成功时间。

批次是共享一个不透明、按请求者隔离身份的一组显式提交任务，核心绝不从路径推导身份。群组与频道标识仅作为文本元数据保存：`origin_group_id` 仅在 Telegram 提供来源时表示原始群组或频道对等方，`channel_id` 仅表示原始/来源频道；核心不会从其中一个、请求者或私聊推导另一个，不可用或有歧义时显示 `N/A`。只有预期大小大于 1、任务数量恰好等于预期、全部处于终态且所有成员均成功时，批次才符合完成操作条件。紧凑的按提交者通知行是该操作的持久发件箱；一个事务检查资格并让通知在 `pending`、`claimed` 和 `sent` 间转换，发送失败或标记 `sent` 失败会释放领取。

服务运行期间由具备生命周期的调度器以有界分页发现符合条件的 pending 通知与陈旧领取，在启动时及固定轮询中重驱动，并由任务完成唤醒。因此送达不依赖后续完成回调。`sent` 为终态。调度器在多次尝试间创建或复用恰好一个不透明 Move-all 交互，绝不把持久交互视为 Telegram 已接收消息的证据。送达为至少一次：若 Telegram 已接收发送但 SQLite 尚未记录 `sent` 时进程崩溃，重试可能重复聊天通知，但会复用同一交互和回调身份并最终收敛到 `sent`。不声称跨外部发送与本地提交的恰好一次送达。

## 存储与完成

存储把配置下载根划分为共享 `inbox/`、共享 `archive/` 与隐藏 `.partial/`。Worker 先在 SQLite 中预留不会冲突的 Inbox 名称，再写入单任务 partial 区域；同步文件后以不覆盖语义提交，最后在同一数据库事务中完成任务和目录记录。解析路径必须位于根目录内，并拒绝符号链接及异常文件系统对象类型。

重命名和归档操作会先持久化文件系统意图，再移动文件、更新目录与操作者审计，最后删除意图。启动对账可完成安全的中断移动，或拒绝已变化及有歧义的状态。另一个一次性对账器会把已跟踪的 v0.1 UUID 目录输出移入 Inbox，且不会覆盖无关文件。

Provider 失败分为永久失败和可重试失败。可重试失败采用有上限的指数延迟，并遵守更长的 Telegram 限流等待时间。Bot 终态通知为尽力发送，通知失败不会改变已持久化的下载结果。成功消息使用最终目录名称、逻辑 `/download/<相对父目录>`、存储大小、持久化开始/完成时间转换后的服务器本地 `HH:MM:SS`、耗时秒数和平均 KB/s。缺失值显示 `N/A`，绝不使用宿主绝对路径或通知发送时的时钟。
