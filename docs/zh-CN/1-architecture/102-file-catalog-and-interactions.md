# 102 — 文件目录与交互

[English](../../1-architecture/102-file-catalog-and-interactions.md)

TGHarbor v0.2 将下载执行与下载后整理分离。任务描述获取与重试状态；已存储文件记录描述当前文件名、位置和整理历史。

## 隐私与元数据

Telegram Provider 可提供规范化并截断为最多 160 个 Unicode 字符的消息文本、原始文件名、MIME 类型和大小。TGHarbor 不持久化完整消息正文。受限标题只用于展示，不作为文件名。日志不得包含消息文本、Telegram 链接、凭据、access hash 或原始 Telegram 对象。

## 持久模型

Schema v4 保留任务上的受限展示元数据、预留 Inbox 名称以及 v3 引入的批次、尝试、暂停与来源元数据字段，并增加：

- 可为空的不透明 `batch_id` 和默认值为 1 的 `batch_expected_size`；
- 可为空的 `started_at` 与 `finished_at` 尝试时间戳；
- 默认值为 false 的持久 `resume_required` 标记；
- 以文本保存的 `origin_group_id` 与 `channel_id`，不假设 Telegram ID 的宽度或格式；
- 交互会话上可为空的 `batch_id`，单文件操作仍以现有任务关联为锚点；
- 交互会话上可为空的 `prompt_message_id`，锚定渲染提示所用的 Bot 消息，使后续文本输入可以编辑该消息而无需再发一条；
- 显式的 `working-confirm` 与 `working-confirm-new-directory` 步骤，记录领取时消耗的是哪一个确认，使重启恢复能还原准确的原确认而不是猜测；旧式通用 `working` 行恢复到安全的 `ready` 重试状态；
- 显式且不可操作的 `result-pending` 与 `retry-pending` 步骤，复用现有交互行作为紧凑的持久结果投递发件箱；schema 仍为版本 4，此行为无需迁移；
- 每个提交者一行的紧凑 `batch_notifications` 完成通知状态。

从 schema v3 迁移的交互行获得 NULL 提示锚点。锚点属于内部 Telegram 消息标识，绝不进入回调载荷或日志。

同时保留：

- 每个完成输出对应一个**已存储文件**，包含根目录相对路径、原始/当前名称、大小、MIME 类型、Inbox/Archive 状态和最近操作者；
- 一个**交互会话**，包含授权操作者、动作、步骤、目标文件或批次、待定输入和过期时间；
- 一个**审计事件**，包含操作者、操作、来源/目标路径和时间。

索引只用于领取、恢复任务和批次查询：现有领取索引，加上针对 `resume_required` 和非空 `batch_id` 的部分索引，以及陈旧通知领取索引。原始批次与来源标识不会进入回调载荷。

所有授权用户都能查看和整理共享目录；任务状态与取消仍按请求者隔离。迁移在显式事务中逐版本执行，保留已有记录并拒绝更新版本；失败步骤会先回滚再停止初始化。迁移后的回滚必须同时恢复数据库和下载根目录备份。

## 尝试计时与重启继续

领取一次尝试时设置 `started_at`。可重试失败在等待期间清除它，下次领取写入新值。完成、终态失败或取消会在同一原子更新中设置 `finished_at`，因此耗时与完成通知描述实际发生的尝试和终态转换。重启继续不会重置重试计数。

运行中任务的重启恢复有三种结果：已持久化取消进入 cancelled；尝试次数耗尽进入 failed；符合条件的中断任务进入带 `resume_required` 的 pending。暂停任务不可领取，并在重复重启后保持暂停。提交者可以列出自己的暂停任务，并继续全部或选定子集。继续操作按提交者授权、幂等、保留尝试计数、清除暂停标记并唤醒 Worker。普通 pending 任务不受影响。

启动时还会恢复持久的工作中交互。`working-confirm` 回到 `confirm`，`working-confirm-new-directory` 回到 `confirm-new-directory`，并保留待定输入和提示锚点；旧式通用 `working` 行回到 `ready` 并清除待定输入。该恢复有意选择安全、可重复的确认或重试动作，而不是猜测被中断的文件库操作已经造成破坏；底层整理操作对已移动或已归档成员本身是幂等的。

恢复事务是原子的，并在回调处理器接受事件前返回准确恢复的会话，而不仅是数量。Telegram 客户端与控制器启动后，适配器会尽力把每个持久提示锚点编辑为与恢复状态匹配的卡片：确认保留待定文件/目录上下文以及 Confirm、Back、Cancel；`confirm-new-directory` 使用 Create and move；旧式 `ready` 行显示带有动作相应 Retry 或 Choose folder 控制及 Cancel 的中断动作卡片。锚点缺失或可证明无法编辑时，会发送恰好一条替换消息并通过比较并交换绑定。每个会话相互隔离：编辑、发送或仓储失败只记录步骤、结果、类别和错误类型，不含 ID 或内容，绝不中止启动或改变任务状态。若编辑与发送均失败，数据库状态仍保持恢复，运维者通过 `/files`、`/history`、`/dirs`、`/rename` 或 `/archive` 继续；系统不会声称可见恢复成功。

## 持久结果投递

已提交的整理结果必须能在最终编辑失败或取消后继续存在。一行交互记录就是持久发件箱条目：`result-pending` 保存已提交的单文件结果或完全终态的批次结果，`retry-pending` 保存 Retry 卡片尚未确认可见的部分批次结果。两种步骤都不可操作，任何回调都无法消耗它们，并且都忽略可操作过期时间，因此已过期但未投递的行仍可恢复。被搁置的 `working`、`working-confirm` 或 `working-confirm-new-directory` 领取即使已超过原始过期时间也会被恢复，因为它处于无法操作的搁置状态；恢复会按现有交互生命周期写入新的可操作过期时间。其他已过期的可操作行保持原有的陈旧语义。

文件库操作达到成功或幂等终态后，适配器原子地把已拥有的工作领取转换为 pending 步骤；对单文件还在同一 `BEGIN IMMEDIATE` 事务中删除该任务的其他完成动作行。只有在最终投递已知成功，并通过预期步骤与预期锚点比较并删除后，pending 行才会被移除。终态卡片没有按钮；Retry 卡片只有在已知送达且其实际锚点完成比较并交换后，才变为可操作的 `ready`，并且该转换会写入新的可操作过期时间。投递仍为编辑优先，仅对可证明不可编辑的错误集合发送恰好一条替换消息。发送成功返回但没有正消息标识时视为模糊投递：既不会消耗终态行，也不会用旧锚点把重试行提升为 `ready`。超时、flood wait、网络或 RPC 模糊错误、未知失败和客户端取消都不会回退发送，并保留 pending 行。

文件库变更及其到 `result-pending` 或 `retry-pending` 的立即转换构成一个取消安全的关键区，包括新建目录与批次整理。持久化、投递和成功清理同样受 shielding 保护。工作开始后的外部取消会让操作与 pending 状态写入完成后再向上传播；取消绝不会被吞掉。提交前失败或取消仍可恢复原确认，但已提交的效果绝不会恢复重复确认。这只是异步取消保证：文件系统写入与目录行之间发生 SIGKILL 或掉电时，依赖幂等对账与重放，而不是跨系统原子性。重复的相同文件移动和重复创建已存在的相同目录不会追加重复审计行，因此恢复重放是安全的。

启动只在存储整理对账之后列出全部 pending 行，并在回调处理器启动前恢复它们。没有固定积压上限：即使较早的行反复失败，后面的行仍会在同次启动中被尝试，且每行失败相互隔离。每张卡片只按当前已授权的任务与目录状态重建，绝不使用持久化消息文本或宿主路径，也绝不重跑单文件或批次整理 API。操作者已不再授权的行会被跳过并保留。编辑失败或模糊错误会让 pending 行保留到下次启动。

## 批次接收与来源元数据

批次身份由可信适配器在提交时显式提供，对核心不透明。Telegram 相册处理器把同一相册的每条媒体以固定版本前缀、请求者 ID、配置的会话/客户端身份、来源聊天和 Telegram `grouped_id` 生成的确定摘要提交；原始组件绝不进入回调或日志。单消息处理器忽略分组消息，因此相册只提交一次。直接链接指向相册一个成员时不会远程展开，仍为单成员任务。

`origin_group_id` 与 `channel_id` 是可选文本元数据。`origin_group_id` 仅在 Telegram 提供无歧义对等方时表示原始群组或频道；`channel_id` 仅在来源为频道时设置。核心与适配器都不会从其中一个、请求者或私聊推导另一个。仅当所有成员暴露同一无歧义对等方时才使用转发元数据；私聊、不可用或有歧义时保持为空并显示 `N/A`。

只有预期大小大于 1、任务数量恰好等于预期、全部处于终态且所有成员均完成时，批次才符合“全部下载完成”操作条件。部分失败或取消不会产生移动全部操作，但仍可通过按提交者的进度计数查询。持久通知行是带小型状态机的发件箱：

```text
不存在 --符合条件领取--> claimed --发送成功且标记 sent 成功--> sent（终态）
claimed --发送失败或标记失败释放--> pending --领取--> claimed
claimed --陈旧领取恢复或启动释放--> pending 或由替代者领取
```

资格检查与领取在同一事务中执行，因此并发 Worker 与调度器不能同时拥有同一通知。`sent` 是终态，绝不会被重驱动。发送失败会释放领取。调度器以有界分页列出通知缺失、pending 或处于陈旧领取的符合条件批次，并在服务运行期间按固定轮询重试；任务完成会唤醒同一调度器。启动恢复会释放所有持久领取，因为单实例锁证明不存在仍存活的旧发送者，随后立即执行一次重驱动。后续领取也可无需重启接管陈旧领取。

每次投递尝试都会调用幂等的确保步骤，为请求者与不透明批次 ID 创建或刷新恰好一个持久交互，用该交互发送一条 `Move all to new folder` 消息，并只在送达后标记通知 `sent`。回调只携带交互 ID 与绑定步骤的动作标记，因此重放按钮仍可解析且保持幂等。

持久交互绝不作为 Telegram 已接收消息的证据：创建交互后、发送前崩溃会被重驱动为真实发送。发送失败时保留交互以便复用并释放领取。发送成功但标记 `sent` 失败时，适配器释放领取，后续重试可能再次发送聊天通知，但会复用同一交互与回调身份并最终到达 `sent`。这是有意的至少一次送达。Telegram 接收与 SQLite 提交属于两个系统，实际送达后超时或两步之间崩溃会使偶发重复无法避免；实现绝不声称跨该外部边界的恰好一次送达。

相册移动仅限 Inbox。`LibraryAPI.organize_batch(actor_id, batch_id, target_directory)` 只移动操作者批次中当前位于 Inbox 的成功成员。它复用现有整理路径完成路径校验、中断移动恢复、冲突后缀、审计和目录更新。操作逐文件执行，成员之间非原子。已归档成员会跳过；成功但没有目录记录的任务报告为 missing；未成功成员报告为 not ready；存储或目录失败按文件报告且不回滚其他文件。重放是幂等的。结果只暴露已移动、跳过、失败、已移动、缺失和未就绪计数及稳定类别，绝不包含绝对文件系统路径。其他提交者不能查询或移动该批次。Telegram 适配器只调用此 API，绝不直接读取路径、存储或 SQLite。

存在 failed 或 not ready 成员时属于可重试结果：已领取行转换为 `retry-pending`，回复提供持久的 `Retry move` 操作，只有在卡片已知送达且实际锚点完成比较并交换后，该行才变为可操作的 `ready`。后续尝试可移动剩余 Inbox 成员，已归档成员会跳过。仅 missing 属于终态，因为没有目录行可供重试。完全移动或全部已移动的结果（包括仅 missing 的结果）转换为 `result-pending`，只有在终态卡片已知送达后才被移除；之后重放的确认或重试标记都会作为陈旧请求被拒绝且不产生变更。重启只从目录重建卡片，绝不重跑批次操作，重试只影响仍在 Inbox 的成员。

## 存储布局

```text
downloads/
├── inbox/       已完成、等待整理的文件
├── archive/     授权用户管理的目录
└── .partial/    隐藏的按任务隔离临时文件
```

Telegram Provider 在写入存储前按固定优先级解析媒体名称：任务显式目标名、非空 Telegram 文件名，最后是 `telegram_<消息 ID>` 加经过校验的扩展名。扩展名必须是简短的小写 ASCII 字母数字后缀；否则使用保守的显式 MIME 映射（JPEG、PNG、WebP、MP4），未知或不安全元数据回退到 `.bin`。最终文件名和路径清理仍由 Storage 负责；MIME 推断保留在 Telegram 适配器内。

期望名称必须清理；发生冲突时在扩展名前追加短任务标识，绝不覆盖无关文件。所有路径保持在根目录以内。绝对路径、路径遍历、空段、符号链接组件和异常文件类型都会被拒绝。完成与整理使用同文件系统原子移动并同步目录。

Worker 解析并持久化元数据、预留 Inbox 名称、下载到任务隐藏临时路径、原子提交到 Inbox、创建目录记录，然后发送操作按钮。重命名/归档在移动前持久化意图；重启后恢复过程只完成可证明的结果，否则报告冲突且不删除内容。

现有 v0.1 UUID 目录属于旧输出。对账只处理具有已跟踪普通文件的 completed 任务，预留防冲突名称，逐个移动文件，并将歧义或失败项保持原状供运维者检查。

## Bot 交互与查询

完成动作包括 `keep`、`rename`、`archive` 和 `rename-and-archive`。成功下载还会显示 `Download Completed`、最终目录文件名、逻辑 `/download/<相对父目录>`、以 MB 表示的存储大小、转换为服务器本地 `HH:MM:SS` 的持久开始/结束时间、耗时秒数、平均 KB/s、请求者 ID 以及来源群组/频道或 `N/A`。查询失败会回退到受限任务数据，不改变已完成任务。多成员相册成功后可产生一条持久 `Move all to new folder` 交互；单任务绝不显示。目录选择、新建目录、确认、取消和分页属于持久交互步骤。需要文本输入的提示会把渲染它的 Bot 消息持久化为提示锚点。回调数据只携带不透明交互 ID 与动作标记；批次 ID 与提示消息 ID 只存在于交互行。每次回调都重新检查授权、过期时间、操作者所有权和目录状态。

目录按钮携带一个不透明短摘要，绑定所显示的目录及当前显示顺序，而不是列表索引。适配器通过 Library API 重新获取目录并对照当前列表解析摘要。若顺序或成员发生变化，回调会作为陈旧请求被拒绝，不改变交互或文件库，并回复刷新后的选项。因此已渲染按钮在排序变化后绝不会解析为其他目录，且载荷保持在 Telegram 的 64 字节限制内，不包含目录名称或路径。

每个回调都会在目录、文件库或文件系统操作开始前立即确认一次，且恰好一次，使用简短或空的 spinner 答复。该答复绝不是主要反馈。提示、成功结果、过期或陈旧选择、授权与领域错误以及意外失败都会生成持久聊天反馈。当 Bot 消息已经承载该交互时，投递通过底层客户端 `edit_message` API 使用回调聊天与消息身份进行编辑优先处理；适配器绝不在显式确认后使用 Telethon 的 `CallbackQuery.Event.edit` 或 `respond`，因为 Telethon 1.45 中二者都会隐式再次确认。Telegram 的“消息未修改”结果视为成功。只有能证明消息无法编辑的错误（无效或缺失 ID、需要作者权限、禁止写入、编辑已过期）才会回退为恰好一条替换消息。所有保留 Back、Cancel、Retry、目录或分页控制的卡片都通过同一个辅助函数投递，该函数返回实际编辑或替换后的消息 ID，并把锚点从预期旧消息 ID 比较并交换到该 ID；竞争失败的替换按钮会被禁用或标记为陈旧。超时、flood wait、超长消息、模糊 RPC 或网络错误以及任意异常不会重复反馈：它们返回一条通用安全投递失败，并让交互保持可恢复。文本长度在尝试超长编辑或发送前校验。意外失败只记录结果、投递类别、错误类型和延迟，不记录操作者 ID、交互 ID、消息 ID、回调载荷、名称、路径、消息文本或 Telegram ID。

同一条单卡片锚点覆盖目录选择、新建目录、确认、工作状态、成功、部分失败和取消。目录选择包含上下文标题、下一步动作、按最近使用顺序排列的现有目录、新建目录和取消，并在没有目录时明确说明。确认步骤对已有目录提供 `Move here`，对新目录提供 `Create and move`，并带 `Back` 与 `Cancel`。卡片在文件系统或文件库操作前显示可见的工作状态，随后编辑为结果。保留操作会保留完成摘要，并说明文件仍在 Inbox。

Bot 会为默认作用域和全部私聊作用域尽力注册命令菜单，准确命令为 `start`、`files`、`status`、`history`、`dirs`、`cancel`、`stats`、`rename`、`archive`、`mkdir` 和 `help`。每个作用域相互隔离失败，只记录结果、作用域和错误类型，并在启动后、通知与 Worker 稳态前运行。

`/files` 与 `/history` 共享内容与按钮构建器。调用命令会发送一条新消息，而分页回调会原地编辑来源 Bot 消息。分页回调先以原子操作消耗并返回其准确、已授权、未过期且动作与分页步骤仍匹配的交互；第一个并发回调拥有该标记，其他回调在创建后继交互或编辑之前即被视为陈旧。后继交互只在取得所有权后创建，并以回调消息作为初始提示锚点，因此在同一消息上的编辑优先投递无需重新绑定。投递在取消 shielding 保护下完成，并在重新抛出待处理取消前检查实际结果，所以已经可见的后继卡片不会因回滚而失去按钮。若编辑错误证明消息不可编辑，会发送恰好一条带有效上一页/下一页按钮的替换消息，并在受 shielding 保护的关键区内把所有后继锚点从原消息移动到替换消息。若该重新绑定失败，会禁用替换消息、删除后继行、恢复准确的原交互，并重新渲染原卡片（或发送一条重试卡片并绑定），使恢复后的来源标记确实出现在可见卡片中；若原交互在投递期间过期，则改为禁用原卡片。因此只有不存在可用后继卡片时才会回滚到原交互。投递前发生的非回退失败、超长渲染、模糊错误或取消会删除后继交互并准确恢复原始交互。未修改的编辑不会产生重复，重放或并发消耗的分页标记属于陈旧请求且不产生任何变更。

文本路由是确定性的。`/start`、`/help` 和已识别命令保持可用；无任务标记的 `/cancel` 会取消当前文本提示，而 `/cancel <job>` 保持任务取消。其他任何文本（包括未知斜杠前缀文本）会在链接或上传提交前继续活动文本工作流。目录提示会校验相对路径；绝对或斜杠前缀输入会停留在同一提示并显示相对路径示例，绝不创建任务。确认步骤等待期间发送文本会重新渲染该确认，而不是提交新的下载。

每个操作者只有一个活动文本工作流。激活在一个 `BEGIN IMMEDIATE` 仓储事务中验证保留行存在、属于该操作者、未过期、匹配预期来源动作与步骤，并转换到请求的等待或确认状态；只有完成转换后，同一事务才删除该操作者其他活动重命名、归档或批次移动工作流。分页交互和其他任务的就绪完成按钮绝不会被删除，因此文本路由保持明确且不会禁用无关卡片。并发激活两行会恰好留下一个活动工作流，绝不会为零。确认工作通过把授权且未过期的确认原子转换为 `working-confirm` 或 `working-confirm-new-directory` 来领取；只有获胜者执行文件库或文件系统操作，重复回调报告操作正在处理且不覆盖获胜者卡片。可恢复失败会恢复确认或就绪状态，并把任何替换后的 Back/Cancel/Retry 卡片重新绑定锚点后渲染其控制；成功会把已领取行转换为 `result-pending`，并且只在终态卡片已知送达后移除。文件库变更及其到 pending 的立即转换构成一个取消安全关键区：工作开始后的外部取消会让操作与 pending 写入完成后再传播；提交前失败可恢复原步骤与提示锚点，已提交效果绝不恢复重复动作。硬进程停止由启动恢复处理：持久化的 `working-confirm`/`working-confirm-new-directory` 行回到准确的原确认并保留待定输入与锚点，旧式通用 `working` 行回到 `ready` 并清除待定输入；即使原过期时间已过也会恢复，并写入新的可操作过期时间。当回调消息 ID 与存储的提示锚点不匹配时，该工作流回调属于陈旧请求且不产生变更。无法解析的载荷、已消耗标记的重放或与步骤不匹配的标记会返回一次性反馈且不编辑较新的卡片；活跃完成卡片上的过期或未授权反馈会编辑该卡片。

重启恢复与 Telegram 启动完成后，Bot 会向每个授权用户发送一条尽力发送的初始化消息，包含包版本、带时区的服务器本地 ISO 时间戳及该用户的暂停数量。数量大于零时创建持久查看与继续交互；为零时说明没有中断任务并省略它们。查看按请求者隔离，不暴露宿主路径或他人任务。继续只为该请求者调用 `JobAPI.continue_paused()`，仅清除其暂停任务、唤醒 Worker 并报告恢复数量。重放是幂等的，跨用户回调会被拒绝，重复重启会让未继续任务保持暂停。

回调标记与交互动作和当前步骤绑定。与当前步骤不匹配的标记（包括在名称或目录输入后重放的完成动作）会在任何状态变更前作为陈旧请求拒绝，从而保留待定输入。“新建目录”是显式确认步骤：输入路径会被保存并显示为将要创建的目录，确认时先通过 Library API 创建归档目录，再整理文件。创建已存在的目录是幂等的。预期的文件库失败会映射为稳定消息，区分无效名称或目录、目录中文件缺失或文件库状态已变化；原始异常文本（包括路径）绝不会发送到聊天或写入日志。

目录列表与归档选择按钮只包含归档根目录下仍然存在的目录，并按最近使用时间排序；该时间来自现有审计与已存储文件时间戳，包括空目录的创建审计行。最近使用时间相同或没有使用历史的目录按不区分大小写的字母顺序排列。Library API 结合存储存在性与仓储最近使用数据；Telegram 适配器不直接查询 SQLite 或文件系统。

- `/status` 显示请求者自己的 pending/running 任务。
- `/history` 分页显示请求者自己的终态任务并支持筛选。
- `/files`、`/dirs` 和 `/stats` 读取共享目录。
- `/rename`、`/archive` 和 `/mkdir` 允许授权用户修改共享目录并记录其 Telegram ID。

短任务 ID 只有在命令授权范围内唯一匹配时才会接受。
